# معماری فنی NetGuard

## 1. اهداف معماری

- هزینهٔ زیرساخت: فقط سرویس‌های دارای پلن رایگان واقعی؛ trial و قابلیت‌های پولی جزو راه‌حل اصلی نیستند.
- نزدیک به زمان واقعی: هدف اولیهٔ جمع‌آوری برای منابع مناسب، هر ۵ دقیقه است؛ اجرای زمان‌بندی best-effort است و SLA ندارد.
- استقلال جمع‌آوری از وب‌سایت: خاموش یا خواب بودن وب‌سایت نباید اجرای Collector را متوقف کند.
- ماندگاری داده: داده‌ها نباید روی filesystem موقت Render ذخیره شوند.
- سادگی: در شروع یک سامانهٔ ماژولار با workerهای مستقل؛ نه Kubernetes و نه تعداد زیادی microservice.
- قابلیت ممیزی: هر مشاهده باید قابل ردیابی به منبع و زمان آن باشد.

## 2. معماری انتخاب‌شده برای شروع

```text
Public Sources
    │
    ├── IODA
    ├── RouteViews / RIPE
    ├── OONI
    ├── RIPE Atlas public measurements
    └── M-Lab historical datasets
            │
            ▼
GitHub Actions scheduled collectors
(Python jobs; source-specific schedules)
            │
            ▼
Validation → Normalization → Deduplication
            │
            ▼
Supabase PostgreSQL
+ PostgREST API
+ Realtime
            │
      ┌─────┴───────────┐
      ▼                 ▼
React + Vite        FastAPI (optional,
Render Static Site  non-critical endpoints)
      │
      ▼
Monitoring Center
(Realtime subscription + polling fallback)
```

### اجزای اصلی

**Frontend**
- React + JavaScript + Vite.
- استقرار به‌صورت Render Static Site.
- محتوای استاتیک به سرویس Backend خواب‌پذیر وابسته نیست.
- با Supabase از طریق API عمومی فقط‌خواندنی و سیاست‌های RLS ارتباط می‌گیرد.
- تغییرات جدید را با Realtime دریافت می‌کند و در صورت قطع اتصال، polling پشتیبان دارد.

**Database و API داده**
- PostgreSQL روی Supabase Free، مشروط به تأیید فعال بودن پلن رایگان و ظرفیت پروژه.
- Supabase REST/PostgREST برای خواندن داده از داشبورد.
- Supabase Realtime برای ارسال تغییرات تازه به کلاینت‌ها.
- RLS برای محدودکردن داده‌های قابل مشاهدهٔ عمومی.
- migrationهای SQL در Git؛ تعریف schema و policyها نسخه‌بندی می‌شود.
- پروژهٔ Supabase موجود فقط پس از بررسی پلن، وضعیت، quota و داده‌های فعلی برای این معماری انتخاب می‌شود.

**Collectors**
- Python jobs که در GitHub Actions اجرا می‌شوند.
- زمان‌بندی هدف برای منبع‌های مناسب: هر ۵ دقیقه.
- هر منبع زمان‌بندی، timeout، retry، rate limit و checkpoint مستقل دارد.
- Collectorها مستقیماً به Supabase می‌نویسند و به بیدار بودن Render وابسته نیستند.
- درج داده‌ها idempotent است؛ اجرای دوبارهٔ یک job نباید رکورد تکراری بسازد.

**FastAPI**
- FastAPI در مخزن حفظ می‌شود و برای endpointهای تحلیلی یا API عمومی پیچیده‌تر قابل استفاده است.
- اگر روی Render Free به‌عنوان Web Service اجرا شود، ممکن است پس از ۱۵ دقیقه بی‌درخواستی sleep کند.
- بنابراین مسیر حیاتی داشبورد و تحویل دادهٔ جدید نباید به پاسخ‌گویی دائمی FastAPI وابسته باشد.
- استفاده از FastAPI برای قابلیت‌های غیرحیاتی تا زمان اثبات نیاز، مرحله‌ای خواهد بود.

## 3. استقرار و محدودیت پلن رایگان

### Render
- Frontend به‌صورت Static Site میزبانی می‌شود.
- Render Free Web Service بعد از ۱۵ دقیقه بدون ترافیک ورودی sleep می‌شود و بیدارشدن آن ممکن است حدود یک دقیقه طول بکشد.
- filesystem وب‌سرویس رایگان موقت است؛ محل ذخیرهٔ دادهٔ پایدار نیست.
- Render Cron Job انتخاب نمی‌شود؛ طبق قیمت‌گذاری فعلی حداقل هزینهٔ ماهانه دارد.
- Render Postgres Free هم برای ذخیره‌سازی دائمی انتخاب نمی‌شود؛ دیتابیس رایگان آن پس از ۳۰ روز منقضی می‌شود.

### GitHub Actions
- زمان‌بندی workflow حداقل هر ۵ دقیقه قابل تعریف است.
- schedule روی آخرین commit شاخهٔ پیش‌فرض اجرا می‌شود؛ بنابراین workflow جمع‌آوری پس از ادغام و فعال‌شدن در شاخهٔ پیش‌فرض عملیاتی خواهد شد.
- اجرای schedule تضمین ثانیه‌ای ندارد؛ GitHub ممکن است در زمان فشار کاری اجرای آن را به تأخیر بیندازد و در شرایط خاص بعضی اجراها را از دست بدهد.
- زمان شروع واقعی هر اجرا و میزان تأخیر باید ثبت شود.
- از اجرای موازی ناخواسته با concurrency control و قفل مبتنی بر زمان/شناسه جلوگیری می‌شود.

### Supabase Free
- سهمیهٔ فعلی شامل ۵۰۰ مگابایت اندازهٔ دیتابیس در هر پروژه است.
- Free project در صورت فعالیت دیتابیسی ناکافی در یک بازهٔ هفت‌روزه ممکن است pause شود.
- مستندات Supabase می‌گویند درخواست‌های واقعی روزانه معمولاً برای جلوگیری از pause کافی‌اند، ولی تضمین مطلق نیست.
- Realtime در پلن رایگان فعلی ۲۰۰ اتصال هم‌زمان و ۲ میلیون پیام در ماه دارد.
- Free plan فاقد uptime SLA و backup خودکار سطح پلن پولی است.
- مصرف storage، egress، realtime و pause باید پایش شود. دادهٔ خام حجیم و تکراری بی‌دلیل ذخیره نمی‌شود.

این اعداد در زمان پیاده‌سازی دوباره بررسی می‌شوند؛ quota و قیمت سرویس‌ها ممکن است تغییر کنند.

## 4. سیاست تازگی و هم‌زمانی

- زمان‌بندی collector، زمان دریافت منبع و زمان خود مشاهده سه مقدار جدا هستند.
- فیلدهای اصلی زمانی: `observed_at`، `collected_at`، `published_at` (در صورت ارائه توسط منبع)، و `run_started_at`.
- در داشبورد زمان تازه‌بودن بر اساس `observed_at` سنجیده می‌شود.
- Realtime فقط تغییر رکورد را سریع به مرورگر می‌رساند؛ به معنی تازه‌بودن ذاتی دادهٔ منبع نیست.
- polling پشتیبان به‌صورت پیش‌فرض هر ۶۰ ثانیه است و فقط وقتی صفحه باز است اجرا می‌شود.
- معیار stale/unknown برای هر منبع مستقل و بر مبنای رفتار واقعی و مستند آن منبع تنظیم می‌شود.

## 5. مدل دادهٔ اولیه

جدول‌های اولیه:

| جدول | مسئولیت |
| --- | --- |
| `sources` | شناسهٔ منبع، نوع، مستندات، cadence، محدودیت و وضعیت فعال‌بودن |
| `collector_runs` | شروع/پایان اجرا، نتیجه، تأخیر، تعداد رکورد، خطا و نسخهٔ Collector |
| `observations` | مقدار مشاهده‌شده، واحد، منبع، زمان مشاهده/دریافت، محدودهٔ جغرافیایی و کیفیت |
| `geo_entities` | کشور، منطقه، استان و شهر، همراه با شناسه و سطح دقت |
| `events` | رخدادهای تشخیص‌داده‌شده، بازهٔ زمانی، شدت، وضعیت و اطمینان |
| `event_evidence` | شواهد مرتبط با رخداد و سهم هر منبع |
| `domain_classifications` | فهرست‌های تاریخ‌دار `censored_domains` و `sanctioned_domains` با منبع و اعتبار |
| `dashboard_snapshots` | خلاصه‌های آماده برای خواندن سریع داشبورد، در صورت نیاز اندازه‌گیری‌شده |

هر مشاهده حداقل شامل source، signal، entity، observed_at، collected_at، geographic_scope، value/unit، quality/confidence و metadata است. شناسهٔ بیرونی یا کلید یکتای مشتق‌شده برای جلوگیری از درج تکراری استفاده می‌شود.

## 6. کنترل کیفیت و امنیت

- کلید Service Role فقط در GitHub Secrets و محیط‌های امن سرور؛ هرگز در کد مرورگر، مخزن یا log.
- مرورگر فقط از کلید public/anon استفاده می‌کند و فقط viewهای عمومی را با RLS می‌خواند.
- هیچ جدول خامی بدون policy مناسب برای خواندن عمومی باز نمی‌شود.
- ورودی منابع با schema validation، محدودیت اندازه و timeout کنترل می‌شود.
- درخواست‌ها retry محدود و backoff دارند؛ خطای دائمی با retry بی‌نهایت پوشانده نمی‌شود.
- raw response فقط در حد نیاز، با retention محدود یا reference ذخیره می‌شود.
- دامنه‌های اندازه‌گیری مستقیم allowlist شده‌اند؛ scan عمومی، پرترافیک یا بدون مجوز انجام نمی‌شود.
- داده‌های دارای دقت جغرافیایی نامطمئن به سطح پایین‌تر یا نامشخص تنزل داده می‌شوند.

## 7. تصمیم‌هایی که فعلاً نمی‌گیریم

- Kubernetes، Redis، message broker و microserviceهای متعدد.
- Worker دائمی ۲۴/۷ یا سرویس پولی.
- اتکا به Render Free Web Service برای زمان‌بندی یا جمع‌آوری.
- اتکا به cache حافظه‌ای برای دادهٔ تاریخی.
- فعال‌سازی پیش‌بینی ML قبل از گردآوری تاریخچهٔ کافی.
- استفاده از منابعی که مجوز یا هزینهٔ مصرف آن‌ها روشن نیست.
